# Fix plan — working through AUDIT-2026-07-30-FULL, one at a time

One session. **One fix per commit**, in the order below. Nothing is batched: a batch that ships together
cannot be bisected when a phone shows nothing.

## The loop, applied to every single item

No item is "done" until all six steps have happened. Steps 1 and 5 are the ones this project has historically
skipped, and both times it cost a day.

1. **Reproduce the bug as it exists now.** Run something and see it fail. If it cannot be reproduced, the
   finding is wrong or already fixed — stop and say so rather than "fixing" it.
2. **Write the guard first, and watch it go RED** against the unfixed code. A test written after the fix tends
   to be shaped like the fix rather than like the bug.
3. **Make the smallest change that turns it green.**
4. **Sabotage it.** Revert the fix (from a backup copy, not `git checkout` — untracked files do not restore),
   confirm the guard goes red *for the right reason*, restore, confirm byte-identical with `cmp`.
5. **Blast-radius check** — the per-item list below. Ends with `npm test` at zero failures every time, and both
   apps mounting in a real browser (that check is in the suite; confirm it RAN rather than skipped).
6. **Commit alone**, with the reproduction evidence in the message.

**Standing rules.** Branch per theme, never straight to `main`. Rebuild `vendor/` after any `src/` change and
confirm the shipped bundle carries it — a source-only fix is on nobody's phone. Kill stray test browsers before
trusting a suite result. Do not touch production; probes run against a throwaway relay with
`TRINITY_DATA_DIR` in a temp dir.

## 1. `ANALYZE` — the missing database statistics

**Reproduce:** build a 60k-row store, `EXPLAIN QUERY PLAN` the real `#d` query. Expect
`SEARCH events USING INDEX idx_kind_created` and ~10ms. (Already measured: 10.33ms → 0.16ms after `ANALYZE`.)

**Fix:** one `db.exec('ANALYZE')` in `openStore()` (`scripts/event-store.mjs`), after the index creation. Also
after the bulk-import path once item 4 makes it work.

**Guard:** a test asserting the plan for the real query names `idx_dtag`, not `idx_kind_created`. This is the
honest assertion — a timing assertion would be flaky on a loaded box.

**Blast radius — what could this break?**
- Startup cost on a large existing relay. Measure `openStore()` wall-clock on a 200k-row database before and
  after; if it is seconds rather than tens of milliseconds, move it behind a "run if `sqlite_stat1` is empty or
  stale" check.
- Query *plans* change everywhere, not just for `#d`. Re-run the relay tests specifically
  (`scripts/relay-*.test.mjs`, `event-store.test.mjs`) and confirm no result-set changes, only timings.
- `ANALYZE` writes to the database — confirm it works on a read-only or permission-restricted data dir, or is
  wrapped so a failure does not stop the relay booting.

**Risk:** low. **Payoff:** highest in the audit. Do it first.

## 2. "Skip setup for now" permanently closes the restore route

**Reproduce:** on a wiped install, tap Skip; confirm `trinityone.onboarded === true` and that no path reaches
the 12-word restore. (`NostrSheet` has no caller — confirm `setNostr(true)` still appears nowhere.)

**Fix — pick one, deliberately:**
- (a) do not set `onboarded` on skip — smallest, but the wizard then reappears every launch, which is its own
  annoyance; or
- (b) add a "Bring my account back" row to the You sheet, so restore has a permanent home.

(b) is the better product answer and is what the two misleading screens already promise. (a) is one line if the
session runs short.

**Guard:** assert a restore entry point exists outside `IdentityOnboarding` and is reachable without a URL
parameter.

**Blast radius:**
- `onboarded` also gates `promptFollowChurch()` — check the join flow still fires correctly after a skip.
- Adding a row to the You sheet touches `app/screens-chat.jsx`, a classic script: run the duplicate-global scan
  and confirm both apps still mount.
- Do not disturb the wizard's own restore route, which is the one that works.

## 3. Help → recovery-phrase backup is a permanent blank spinner

**Reproduce:** needs a PIN-locked session — `secureGet()` returns `null` when locked. Set a PIN in a browser,
lock, open Help → "Begin backup". Expect a spinner with no close button, for ever.

**Fix:** render the header and close button *above* the early return in `app/screens-help-main.jsx:20-26`, and
add the missing `.catch()` at `:16` (its twin at `app/identity-extras.jsx:128` has one — copy that).

**Guard:** assert the close control renders in the loading state.

**Blast radius:** small and local. Check the same early-return shape does not exist in sibling help screens —
if it does, that is a second instance, not a second bug.

## 4. Members get unlimited PIN guesses; stewards get a lockout

**Reproduce:** hammer `tryUnlock` in `app/identity.jsx` — confirm no counter, no delay, unbounded.

**Fix:** port the console's implementation (`app/steward-root.jsx:489-499`) — persisted escalating cooldown,
5 misses → 30s doubling to a 1h cap. Copy it rather than reinventing; it already handles the reload case.

**Guard:** assert a persisted guard key exists and the delay escalates. Test the *logic*, not wall-clock sleeps.

**Blast radius — the important one here:**
- **Must not lock a legitimate member out of their Bible.** The lock screen deliberately still offers "Read the
  Bible without unlocking" — confirm that survives.
- Confirm the cooldown cannot be cleared by reinstalling *without* also destroying the key (it should be
  equivalent, but check what a wipe does to the guard key).
- Confirm a *successful* unlock clears the counter.

## 7–10. The cross-tenant scoping fixes — probably a separate session

`accept()` builds one relay-wide `isMember`; six write rules ask that when they mean "of *this* church". The
primitive already exists (`memberIn(m, cp)`, used by the push notifier).

**Order:** open-group chat (`:1483`) → safety/slots/availability (`:1436`, `:1420`, `:1433`) → the safeguarding
`MINORS` union (`:1409`, `:1433`) → care need/skip ownership (`:1409`, `:1424`, plus `idOwnerOk` in `note()`).

**Fix them as one theme but commit them one at a time**, each with its own failing case from item 6.

**Blast radius — this is the security spine, so:**
- Every fix must keep a **control that still ACCEPTs**: a genuine member of the church must still be able to
  post, respond to a safety check, sign up for a slot and open a care need. Scoping too tightly silently
  disables real members, which is worse than the finding.
- `MINORS` is a deliberate relay-wide union for the DM gate — do **not** scope that use. Only the two in
  `accept()`.
- Re-run the whole relay suite, not just the new cases.
- **Latent, not live** (a8 hosts one church, self-registration locked), so there is no reason to rush these
  into the same session as items 1–5.

## Realistic scope for one session

**Items 1–5 plus 6.** Those are the cheap, certain ones, and item 6 sets up everything after it.

Items 7–10 touch the authorization spine. They are latent, they deserve their own session with the phone
attached, and rushing them behind five other changes is exactly how a batch becomes unbisectable.

## When to stop and ask

- A reproduction that will not reproduce — the finding may be wrong. Say so; do not fix a phantom.
- Any fix that needs a decision rather than a correction (item 2's (a)-vs-(b) is the obvious one).
- Anything that would require touching production or weakening a shipped security setting to test.
