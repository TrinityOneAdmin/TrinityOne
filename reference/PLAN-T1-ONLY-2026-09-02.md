# Plan: only TrinityOne software talks to TrinityOne software

**DECIDED 2026-09-02 by the owner.** Supersedes the admission half of
`PLAN-CLOSED-RELAY-NETWORK-2026-09-01.md` and all of `PLAN-ENROLMENT-GAP-2026-09-02.md`.
Branch `relay/closed-network`, tip at time of writing `741109a`.

## The rule

> **A relay is admitted if, and only if, it proves it is running TrinityOne relay software.
> Nothing else is consulted.**

The proof is C2: `GET /relay-identity?nonce=<32 hex>` returns a `kind-27235` event signed by the
relay's key, carrying our nonce. The client verifies the signature, the nonce, the kind and the
freshness (`src/relay-identity.src.js`, ±300s). Measured 2026-09-02: `relay.damus.io` and `nos.lol`
return strfry's default HTML; a TrinityOne relay returns the signed proof.

**Why this rule and not a stricter one.** `DOMAIN.md` records the owner's definition of a
non-TrinityOne relay as *"people that run our specific relay software"*. This rule is that sentence,
implemented literally. The stricter rule — "a box **my church** specifically chose" — is what produced
the church-signed document, enrolment, automatic discovery, and four blockers. The owner chose the
looser rule with the gap below stated.

### What this rule gives up, stated plainly

Someone who **deliberately** runs our relay software can be admitted. They would learn the
pubkey-level social graph of any church that talks to them: congregation size, group membership,
care rota, RSVPs, and **which member keys are flagged as children**. They would **not** learn names
(`trinityone/name:` is sealed in both fields) or message contents (kind-1, kind-4, journal, notes,
prayer, clearance and guardnotice are all encrypted at rest — measured off a live relay, `d35494e`).

They would also still need their address to reach a church's relay list. C1 (merged) stopped the
product suggesting relays we do not run; C5 (merged) gates every path by which an address is pushed
at a client — `?relay=`, `?relayname=`, `refreshNamedRelays`, `discoverRelayOffers`, backup restore.
Under this plan those gates now ask "does it prove it runs our software" instead of "is it vouched",
which is weaker but not absent.

**An architecture review dissented** and recommended the stricter rule. The owner decided after the
trade was stated. Recorded so nobody re-opens it without new information.

## The changes, precisely

### 1. `proveRelay()` admits on proof alone — `src/relay-net.src.js:162`

Today the function requires a valid proof **and then** one of three roots, returning `{root:'',pub}`
if none matches. Change it to return admitted once the proof verifies.

**Keep computing the root and keep returning it**, for diagnostics and because it makes a future
re-tightening a one-line change rather than an archaeology exercise. Admission stops depending on it.

```
proof fails            → { root:'', pub:'' }        (unchanged: fail closed)
proof succeeds         → { root:<canonical|origin|church|software>, pub }   ← admitted
```

Do **not** delete `canonicalPinsFor`, `sameOriginRelay`, `parseRelayNet` or the `netEntries` dep. They
are cheap, tested, and are the re-tightening path. Mark them clearly as informational.

**Shared-code obligation (CLAUDE.md §2):** `proveRelay` has exactly two consumers — `isNetworkRelay`
(:198) and `createRelayGate` (:299). The gate is consumed by `fellowship.src.js:684` and
`steward.src.js:800`, and reached through `_gate.admit` / `.admits` / `.refresh` at
`fellowship.src.js:710, 2718, 2724, 2985, 5263` and `steward.src.js:669, 817, 1317, 6871`. **All of
these stay unchanged** — the predicate loosens, the plumbing does not. Enumerate them in the commit.

### 2. Church creation must await the first proof — `src/steward.src.js:1317`

`_gate.refresh(relaysRaw(), pub)` is fire-and-forget. An established console coasts on the persisted
30-day cache, but **a brand-new church on a fresh device has an empty cache**, so the creation
wizard's first publishes can race the first proof and land on an empty admitted set — a publish error
in the church's first minute of existence.

This is the owner's requirement that a console starting a church reaches relays immediately, and it
is a **code** fix, not a deployment one. It bites under this plan exactly as it would have under the
stricter one, because a proof is still required.

- Church creation **awaits** `_gate.refresh()` over the canonical set before its first publish.
- If nothing proves, **stop with a truthful message** before declaring the church created. Do not
  create a church that cannot publish. Say what happened and what to do; do not say "check your
  connection", which would be false.
- **No grace path.** Do not admit unproven relays "just at creation". Creation is exactly when a fake
  canonical is cheapest to serve to a new church.

The gate's own API anticipates this — `refresh()`'s comment says the app "would rather spend a second
than start with an empty publish set".

### 3. An unconfigured relay must not accept everything — `scripts/gateway.mjs:1826`

`accept()` opens with `if (!CHURCH_PUBS.size) return true;   // unconfigured = open`. A freshly
installed TrinityOne relay accepts **all writes from anyone**. Under this plan that matters more, not
less: any box running our software is now admitted by clients, so an unconfigured one is reachable.

Fail closed instead — **but check the first-registration flow before changing it.** A church
registers at a new box via `registerAtRelay` → `/config` (NIP-98). If that path depends on `accept()`
being open while the box is unconfigured, closing it breaks the very bootstrap this plan needs. Prove
which order those happen in before touching the line.

The identical window exists in the media gate at `:204`. Same reasoning; check it separately.

### 4. No UI, and nothing to say

Owner: *"I don't really want a panel to say anything, it should be all under the hood… not allow, and
not look for."* No panel, no confirmation, no steward ceremony, no new copy. The one exception is
change 2's hard-stop, which is an error path on a church that could not be created — not a
notification about relays.

Any existing copy that describes relay vouching or enrolment must be reworded or removed. (Note: an
architecture review twice cited `stew-dashboard.jsx:3169` as saying "then enrol it". **That string
does not exist**; line 3169 is `window.Steward.addRelay(j.url);` and no `enrol` string in the UI
refers to relays. Do not go looking for it.)

## Test obligations

CLAUDE.md §1 (test at the point of use), §3 (never assert behaviour by matching text in `app/*.jsx` —
they ship unbundled, so `false && ` leaves every word intact), §8 (account for the count).

1. **A generic Nostr relay is refused.** Real HTTP, not a stub: serve strfry's HTML shape from a local
   port and assert `proveRelay` returns unadmitted. This is the test that the whole plan is named
   after and it must drive real input.
2. **A TrinityOne relay is admitted**, from a real signed proof over a real socket, on its own port,
   with force-exit.
3. **A forged proof is refused** — right shape, wrong signature; and a replayed proof with a stale
   nonce; and one outside the ±300s window.
4. **Church creation with no provable relay stops and says so**, and does not report a created church.
   Point-of-use: lift and execute the creation path, do not string-match it.
5. **Church creation with a provable relay publishes successfully** — the positive half, or test 4
   passes against a permanently broken feature.
6. Sabotage each, **scoped to the function under test** — near-identical siblings are this codebase's
   house style, so slice the enclosing function, assert the anchor appears exactly once inside it,
   then replace. All-red means the harness died, not that the test is sharp.
7. Re-measure the suite count and account for any movement. It was 2445/0 on this branch; that figure
   is unverified by the last audit and must be re-measured, not quoted.

## Verification before merge

The suite passing is not the gate (CLAUDE.md §6).

**First, always:** the relay process must be newer than `scripts/gateway.mjs`. A stale relay enforces
old gates against new bundles and has produced a false finding three times, including twice on
2026-09-02.

```sh
ps -o lstart= -p $(pgrep -f "gateway.mjs 8000" | head -1)   # must be NEWER than
stat -c '%y' scripts/gateway.mjs
```

Then:

1. **The fleet answers the challenge.** Both canonical relays returned **HTTP 404** on
   `/relay-identity` on 2026-09-02. This is the hardest precondition in the plan.
   ```sh
   N=$(head -c16 /dev/urandom | od -An -tx1 | tr -d ' \n')
   curl -s -o /dev/null -w "%{http_code}\n" "https://app.trinityone.church/relay-identity?nonce=$N"
   ```
   Must be 200, **for every box in the fleet**, checked by asking each one.
2. **Cold start on a phone.** Create a church from a mobile browser console with an empty cache and
   confirm it publishes on its first minute. This is the owner's requirement 5 and the hardware-less
   case; a suite cannot prove it.
3. **A device that has never seen the relay** admits it after the fleet update, cold cache.
4. **A generic public relay is refused on hardware**, not only in a test.
5. **Mutual hosting**: two churches on each other's boxes, both publishing and reading.

## Deploy ordering — unchanged and non-negotiable

**Relays before apps.** Ship the apps first and every church loses its relays on the day — and a
church created on a phone could not be created at all, because root 1 is its only route.

1. Update every relay in the fleet.
2. Verify each answers `/relay-identity`, by asking it.
3. Then release the apps.

## Deferred, and deliberately

### Encrypt the social graph the relay does not need

Owner, 2026-09-02: *"We can harden the rsvps, care, event details later."*

A live relay stores these in cleartext: `member:<key>`, `minors:`, `roster:`, `group:`, `rsvp:`,
`careavail:`, `unavail:`, `joinpolicy:`, `event:`, `financekey:`.

**Encryptable later:** `rsvp:`, `careavail:`, `unavail:`, `event:` detail — the relay does not consult
them to enforce anything.

**NOT encryptable without giving up relay-side enforcement:** `member:` and `minors:`. The relay
parses them at ingest (`gateway.mjs:1642`) into `MEMBER_DOCS` and `MINORS_BY`, which feed
`effMemberOf` (:2304) and `minorOf` (:2320) — the read gate and the safeguarding gate. **The relay has
to read the social graph in order to protect it.** Encrypting these blinds the very enforcement this
plan strengthens. It is a genuine tension, not a chore, and anyone proposing it later should be shown
this paragraph first.

Scope before starting: audit which cleartext documents the relay actually reads versus merely stores.
The list above is a starting point, not the finding.

### Left standing

- **`_oneComplete` has no `maxWait`** (`steward.src.js:2247`) while its sibling `_newestByD` does
  (:2405). Measured: a dead port returns `{ev:null, complete:true}` in 7ms, a silent socket at 3001ms.
  Off the critical path now, still a lie in shared infrastructure. Fix when something needs it, and
  fix it with a test that drives a **real** dead socket — an injected flag cannot catch this class.
- **Twelve ungated read subscriptions** (`fellowship.src.js:3596, 3632, 3657, 3669, 3702, 3730, 4994,
  5055, 5069, 5096, 5115, 5223`). No church data leaves on a read; an unproven relay learns metadata.
  Their own piece of work, with its own device pass, because a read gate wrong means a blank screen —
  this codebase's worst failure class.
- **The stricter rule** — root 3 and church-signed lists — stays on the branch as informational code.
  Re-tightening is a one-line change in `proveRelay` plus the enrolment work, if the pilot shows it is
  needed.

## What must not change

- Fail closed on a failed proof. No grace path, least of all at church creation.
- `relayPub` from `/status` or NIP-11 is an unauthenticated string and is **never** proof.
- The bootstrap read at `fellowship.src.js:650` stays unfiltered.
- Backwards compatibility: this **removes** a requirement and adds no document type, so nothing
  published today becomes unreadable. Verify that claim rather than assuming it.
