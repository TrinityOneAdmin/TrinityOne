# Plan: only TrinityOne software talks to TrinityOne software

**DECIDED 2026-09-02 by the owner**, and re-cut twice the same day after audit. Supersedes the
admission half of `PLAN-CLOSED-RELAY-NETWORK-2026-09-01.md` and all of
`PLAN-ENROLMENT-GAP-2026-09-02.md`. Branch `relay/closed-network`.

## The rule

> **A relay is admitted iff it proves, at the address we dialled, that it is running TrinityOne relay
> software. Our own shared machine is additionally identified by its key, not by its address.**

No church-signed lists, no vouching, no enrolment, no UI. A church's own box and a partner church's
box are admitted on the proof alone.

**Owner's decision, in their words:** *"runs our software"*, and — on whether the shared machine's
check should be an address — *"does the check for hole 2 need to be an address?"* It does not. See §2.

### Two holes an audit found in the first cut, and the owner chose to fix both before the pilot

- **Hole 1, the middleman.** A host that runs none of our software forwards `/relay-identity` to a
  genuine TrinityOne relay and passes the real proof back, while terminating the socket itself. The
  corpus and every member's IP land on a box running a reverse proxy. Documented three times in this
  repo already — the essay at the foot of `src/relay-net.src.js`, the comment at `gateway.mjs:561`,
  and an **executable test** at
  `scripts/only-a-relay-this-church-proved-gets-its-data.test.mjs:478-526` that stages a real
  forwarder and requires refusal.
- **Hole 2, the impostor at our own front door.** `wss://app.trinityone.church/relay` ships inside
  every app. Seize or compel that address, answer the challenge with any key, and every device on the
  fleet admits it — no invite, no list poisoning, no adversary effort at all. This is the recorded
  threat model's core scenario.

**Both fixes push the same way: identity is the KEY; an address is a claim that must be proved.** That
is the lesson this codebase already learned from tunnel churn, applied consistently.

## §1 — Fix hole 1: bind the proof to the address dialled

Today the proof already carries the address in a `relay` tag (`gateway.mjs:572`), and
`verifyRelayIdentity` **returns it without checking it** (`src/relay-identity.src.js`, `return { relayPub, url: tag('relay') }`).
And the relay derives that address from the `Host` header (`relayIdentityUrl`, `gateway.mjs:564`) —
which a forwarder controls. Either half alone is insufficient; both are needed.

### 1a. Relay: declare the addresses you answer at, and sign only those

`relayIdentityUrl(req)` currently returns `ORIGIN` if set, else `<x-forwarded-proto>://<host>`.

- A relay gains a **declared address set** (config; the Suite fills it in from its own tunnel/origin
  configuration, so a self-hosting church never types one).
- On `/relay-identity`, take the dialled host. **If it is in the declared set, sign that exact
  address. If it is not, refuse** — do not sign, do not fall back to `Host`.
- The set must hold **more than one entry**: our own shared machine is reached at two addresses
  (Cloudflare and Tailscale) and is one box. A single fixed `ORIGIN` cannot express that, which is why
  the existing note says the naive repair "would still refuse the two canonical URLs".

### 1b. Client: check the signed address is the one you dialled

`verifyRelayIdentity` must compare `tag('relay')` against the URL it dialled, **normalised the way
the connection pool normalises** (`normalizeURL`; a raw string compare that differs by a trailing
slash misses silently — three occurrences of that trap are already recorded in this file). Mismatch →
`null` → refused.

With both halves: a forwarder that passes `Host: evil.example` gets a refusal from the real relay; a
forwarder that rewrites `Host` to the real relay's own name gets a proof naming *that* relay, which
does not match what the client dialled. Both paths closed.

### 1c. The friction this creates, stated honestly

A relay that **cannot name its own address** cannot prove itself. That covers a box reached by raw IP,
or behind a NAT it does not know about. For the pilot this is acceptable — the Suite knows its own
tunnel address and our own boxes are configured — but **it is a real deployment constraint and must be
in the release notes**, not discovered by a church. Decide explicitly what an undeclared relay does:
recommendation is **refuse to sign**, because a relay that signs a `Host` it cannot vouch for is
exactly hole 1.

## §2 — Fix hole 2: our shared machine is a KEY, with addresses as hints

Today `CANONICAL_RELAY_PUBS` maps **address → keys**, and both canonical addresses map to the *same
single key* — proof in the data that the key is the identity and the addresses are two roads to one
box.

Invert it:

> **Our shared relay is key `6a4267558c9990d0391b3472bac9735d33a5e99b5c7cb0e49bdece7ea6b770f2`.
> These addresses are where you will probably find it.**

- The app ships the key as the identity, and the addresses as **starting points** for a cold start.
- **A machine answering at one of our shipped addresses must prove one of our shipped keys.** Anything
  else answering there is refused, however valid its proof.
- Every other address — a church's own box, a partner church's box — is admitted on the proof alone.
  This is **not** an allowlist and does not re-introduce vouching. It is the client declining to be
  fooled about its own defaults.

**Why key-primary rather than address-pinned:** if we move the shared relay, add a third route, or a
tunnel address rotates, nothing breaks and no app update ships, because the key has not changed.
Address-pinning would require a release for a change of road.

### 3b. Church creation must await the first proof — `src/steward.src.js:1317`

`_gate.refresh(relaysRaw(), pub)` is fire-and-forget. An established console coasts on its 30-day
cache; a **brand-new church on a fresh device has an empty cache**, so the wizard's first publishes
race the first proof and can land on an empty admitted set.

Confirmed by the audit: `seedNewChurch` (`app/steward-root.jsx:334`) mints the key immediately,
registration happens at wizard step 1, and `publish()` already waits on `_regGate` ("wait for the
relay to know this church exists", `steward.src.js:1907, 2103-2144`) — built after a measured incident
of exactly this class. The proof race is the same shape one gate over.

- Creation waits on **both** "the relay knows this church" and "the client knows this relay is ours".
  **Join the existing `_regGate` idiom rather than growing a second ad-hoc await.**
- If nothing proves: **do not let the wizard past step 1 and do not declare the church created.** The
  minted key is local and harmless. Say what happened truthfully — not "check your connection".
- **No grace path.** Creation is exactly when a fake canonical is cheapest to serve.

### 3c. An unconfigured relay must not accept everything — `scripts/gateway.mjs:1826`

`accept()` opens `if (!CHURCH_PUBS.size) return true;   // unconfigured = open`.

**The audit settled that closing this is safe for first registration:** `/config addChurch`
(`gateway.mjs:3704-3749`) is HTTP and never touches `accept()`; on an empty relay the private-relay
lock cannot fire, so a fresh box accepts a named, church-key-signed, URL-bound self-registration with
no admin token — the Suite and phone first-run path. `CHURCH_PUBS` loads from `church.json` + env at
startup, not from event replay. Client-side, `_regGate` already orders register-before-publish.

So: **close it to `return false`.** Two things go in the commit: the restore-without-`church.json`
edge (`:486-496`) changes symptom from "silently world-open" to "refuses all writes" — an improvement,
but name the operator-facing failure. The twin in the media gate at `:204` is likewise safe; check it
separately.

### 3d. `ws://` proofs

`setRelays` still admits `ws://` shapes and `relayHttpBase` maps `ws→http`, so a proof fetched over
cleartext is in-path-forwardable *and* the socket is readable. The invite path already refuses
`ws://`; the gate should too, outside loopback. One regex.

## §5 — Verification before merge

The suite passing is not the gate (CLAUDE.md §6).

**First, always:** the relay process must be newer than `scripts/gateway.mjs`. A stale relay enforces
old gates against new bundles and produced a false finding three times, twice on 2026-09-02.

1. **Every relay in the fleet declares its addresses and answers correctly.** Both canonical relays
   returned **HTTP 404** on `/relay-identity` on 2026-09-02.
   ```sh
   N=$(head -c16 /dev/urandom | od -An -tx1 | tr -d ' \n')
   curl -s "https://app.trinityone.church/relay-identity?nonce=$N"   # 200, and the relay tag must
                                                                    # name THIS address
   ```
2. **A forwarder is refused on real hardware**, not only in a test.
3. **Cold start on a phone** — create a church from a mobile browser with an empty cache; it publishes
   in its first minute. The hardware-less case; a suite cannot prove it.
4. **A device that has never seen the relay** admits it, cold cache, after the fleet update.
5. **A desktop Suite first run on hardware** — §3c is the change that bricks first-run if any path
   publishes over the socket before registration.
6. **Mutual hosting**: two churches on each other's boxes, both publishing and reading.

## §6 — Deploy ordering: now stricter than before

**Relays before apps, and the address declaration before the client check.** A client that starts
checking the signed address while relays still sign a `Host` header will refuse everything.

1. Update every relay: `/relay-identity` present, **declared address set configured**, signing the
   dialled address only when it is declared.
2. Verify each box by asking it — 200, and the `relay` tag names the address you dialled.
3. Then release the apps.

Skew is survivable in one direction only: an old app against a new relay is fine; a new app against an
old relay refuses it.

## §7 — Deferred, deliberately

### Encrypt the social graph the relay does not need

Owner: *"We can harden the rsvps, care, event details later."*

Cleartext on a live relay today: `member:<key>`, `minors:`, `roster:`, `group:`, `rsvp:`,
`careavail:`, `unavail:`, `joinpolicy:`, `event:`, `financekey:`.

**Encryptable later:** `rsvp:`, `careavail:`, `unavail:`, `event:` detail — the relay never consults
them to enforce anything.

**NOT encryptable without giving up relay-side enforcement:** `member:` and `minors:`. The relay
parses them at ingest (`gateway.mjs:1642`) into `MEMBER_DOCS` and `MINORS_BY`, which feed
`effMemberOf` (`:2304`) and `minorOf` (`:2320`) — the read gate and the safeguarding gate. **The relay
has to read the social graph in order to protect it.** Show anyone proposing this that sentence first.

Scope before starting: audit which cleartext documents the relay actually reads versus merely stores.

### Left standing

- **`_oneComplete` has no `maxWait`** (`steward.src.js:2247`); its sibling `_newestByD` does (`:2405`).
  Measured: dead port returns `{ev:null, complete:true}` in 7ms. It has exactly two callers, both
  enrolment-only, so it is now unreachable — but leave a one-line "do not call until `_oneComplete` is
  honest" note on `enrolRelayNet` so B0 stays buried.
- **Twelve ungated read subscriptions** (`fellowship.src.js:3596, 3632, 3657, 3669, 3702, 3730, 4994,
  5055, 5069, 5096, 5115, 5223`). No church data leaves on a read; an unproven relay learns metadata.
  Own piece of work, own device pass — a read gate wrong means a blank screen.
- **The verified cache is 30 days.** Admissions granted under this rule persist that long. **Version
  the cache** if the rule is ever tightened.
- **The stricter "a box my church chose" rule** stays on the branch as informational code.

## §8 — Accepted, with eyes open

An admitted relay is a live socket, not just a disk: it sees **member IP addresses, timing and query
patterns**. Under the recorded threat model — lawful compulsion — an IP is the bridge from "pubkeys,
never names" to names. The corpus itself stays as measured: names sealed, contents encrypted, social
graph in pubkeys.

With §1 and §2 fixed, the residual adversary is one who **actually runs our relay software at an
address they legitimately control** and gets that address into a church's list — through a crafted
invite or a steward typing it, both of which C5 already narrows. That is the exposure the owner
accepted.

## §9 — What must not change

- Fail closed on a failed proof. No grace path, least of all at church creation.
- `relayPub` from `/status` or NIP-11 is an unauthenticated string and is **never** proof.
- The bootstrap read at `fellowship.src.js:650` stays unfiltered.
- Identity is the key; an address is a claim that must be proved. Never match membership on a URL.
- Backwards compatible: no document type added, removed or repurposed; the relay does not ingest
  `relay-net` for authority (`gateway.mjs:372`) and `accept()` changes are not retroactive because
  rehydration goes through `note()`, where `accept()` never runs (`:1671-1675`). **Verified by the
  audit, not assumed.**
