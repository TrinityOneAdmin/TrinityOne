## 2. THE FEATURE TO BUILD: "Remember me on this device" (30 days)

Asked for by the owner, 2026-08-05. The honest framing matters more than the code here.

**What it actually trades.** The PIN protects against *someone holding the phone*. So this feature means,
precisely: *anyone who can unlock this phone can open your church account.* There is no version that keeps
the protection and skips the PIN — the PIN **is** the protection. That is still a reasonable choice (people
already rely on the phone's own lock and biometrics), but the copy must say the real consequence, not
"stay signed in".

### Spec

* **A tickbox on the unlock screen**, off by default, ticked deliberately. Never remembered as a default.
* **30 days, then it re-prompts.** The owner chose a bounded window over "never ask again" so a phone that
  is lost and not noticed quickly still re-locks on its own.
* On a successful unlock **with the box ticked**: persist the seed to the OS secure store (native) and record
  an expiry timestamp. On boot, if the expiry is in the future, populate the in-memory seed so `lockNow()`
  is false; if it has passed, clear it and lock normally.
* **Native only.** Do not offer it in a browser — localStorage is far weaker than the hardware store, and the
  threat model is a seized device.
* Reversible from the profile screen, and turning it off must clear both the stored seed and the expiry.
* Copy on the tickbox, or something with the same content:
  > *Stay open on this phone for 30 days. Anyone who can unlock this phone will be able to open your church.*

### Implementation notes

* The lock is `lockNow()` in `app/app.jsx` — `hasEnc() && !sessionMnemonic`. "Remembered" therefore means
  `sessionMnemonic` is populated at boot rather than the blob being removed. **Do not implement this by
  deleting the encrypted blob** — that is exactly the bypass fixed in `23f0798`.
* Keep the encrypted blob so the PIN still works, and so turning the feature off needs no re-entry.
* Reuse `secureSet`/`secureGet` in `src/identity.src.js`, and **check `secureSet`'s return value** — its own
  comment says callers that then delete another copy MUST, and `importMnemonic` still does not (finding M8).
* Expiry belongs beside the seed, not in localStorage alone, or clearing site data extends the window.

## 5. THE LOCK BYPASS — why it happened, because the pattern will recur

Fixed in `23f0798`, recorded because the *shape* is the lesson.

`importMnemonic` deletes the encrypted blob before storing anything. The lock is armed by that blob's
presence. So calling it from the lock screen did not open the lock — **it removed it**. Any valid BIP-39
phrase walked past a locked phone, and the member's notes, journal and outbox survive that transition by
design.

Neither piece was wrong alone. Deleting is correct for a *replace*; presence-checking is correct for a
*lock*. The bug lived only where they met, and nothing tested that seam. `importMnemonic` was safe at its
three existing call sites because all three mean "replace" and all three confirm first — one annotated
*"fixed in ONE of the two copies"*. **This project had already found this shape twice and fixed it
piecemeal. I added a fourth call site and did not look for the other three.**

My checks could not see it: the test was structural, and the device test used the *correct* phrase, so it
looked like success. I never tried a wrong-but-valid phrase and never re-checked that the lock was still
armed.

## 6. OPEN, FROM THE FOUR ADVERSARIAL REVIEWS

### Key lifecycle (`fix/restore-church-key-2026-08-04`)
* **K1** `app/backup.jsx` still removes `church-key.enc` from localStorage only — no `encBlobRemove()`, no
  breadcrumb — so the file-restore path recreates the loss `cd67c7a` fixed. **One-line reorder.**
* **K2** Legacy breadcrumb `'1'` is treated as a WRITE, but on `main` a *removal* writes `'1'`. So upgrading
  mid-removal **resurrects a church the steward deliberately removed**. Resolve legacy by checking the
  marker's absence, not by direction alone.
* **K3** `removeLock` still destroys the only durable copy before the replacement exists — unbounded,
  user-paced window. Same one-line reorder as the restore fix.
* **K4** TOCTOU in `init()`: `encBlobRemoveResume()` and `migrateEncToSecure()` both fire un-awaited and race
  for the same slot; the resume's guard is evaluated before its `await`.
* **K5** `_looksLikeKeyBlob` is a shape check, so it can adopt the *stale but valid* blob that `restoreKey`
  now deliberately leaves behind. Lives in the merge seam.
* **K6** `setPin` can now report failure for a write that landed, leaving the steward behind a PIN they were
  told was rejected — and it shares the "use at least 8 characters" message, which is wrong for that case.
* **K7** The `lock()` guard means an unpersisted seed stays in memory indefinitely (was ≤10 min) while
  `webContentsDebuggingEnabled` is still true. Correct trade; the right remedy is K3, not re-arming the timer.

### Safeguarding / console
* Authority docs (`minors:`/`approved:`/`guardians:`) still publish via `Promise.any` — **one relay wins, no
  verify, no banner** — while the *derived* clearance gets all-relays-must-accept plus a verify read. The
  relay enforces on the former. Nothing ever re-publishes them to a relay that missed one.
* The same-second replaceable race is a real product defect, not just a flaky test: a steward editing twice
  within one second silently loses the second write. `reseat-safeguarding` fails ~2-in-5 on unmodified code,
  and can also pass **for the wrong reason** when the minors write is the one lost.
* `reseatMember` adds the new key to the guardian map but never removes the old one.
* Delegated stewards are fenced only by a JSX conditional; the engine does not enforce it.

### Safety roll-call
* "Care team only" can seal to **nobody** if the care-team roster is unpublished or the fetch fails — both
  member and steward are told otherwise, and the option is offered unconditionally.
* The "stewards" audience reads `_churchRoster` synchronously; on a cold or unauthenticated boot it is empty
  and the reply seals to the church key + starter only. Silent.
* A console outside the audience drops an undecryptable reply silently — "replied but unreadable" renders
  identically to "hasn't responded".

### Engine
* `fetchAsset` falls through on transport failure only, never on bad content — a local candidate that 200s
  with wrong bytes is fatal and permanent, where `main` would have been corrected by the gateway.
