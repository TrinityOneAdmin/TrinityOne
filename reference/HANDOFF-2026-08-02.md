### The one that matters most

**A reconnected child was no longer a child.** When a member loses their 12 words the church cannot give the
account back, so a steward vouches for them and puts a NEW key in their place. Safeguarding is keyed on the
PUBKEY — `minors:` names a key, `guardians:` names a key, and the record that tells a child's own phone it is
a child is SEALED to a key. The reconnect moved the seat and nothing else. Measured against a real relay,
asserting what the child's phone reads:

* the child's phone read **ADULT** — the record was sealed to the dead key, and the `minors:` list it falls
  back to is one the relay deliberately refuses to serve ordinary members, so absence read as adulthood
* **the relay agreed** — `safeguardAllows()` permits anyone to DM a key no church names as a minor, so adult
  DMs and adults-only rooms opened at the same moment
* the next Members visit then **sealed "not a minor"** to the new key — no longer a gap but a church-signed
  wrong answer, after which read-before-write skipped that member for ever
* the **parent link** still pointed at the dead key, so a steward who correctly re-ticked "child" STILL left
  the parent unable to message their own child. That is the half no hand-repair fixes.

The steward was not the backstop: the confirm screen said "ONE thing to finish by hand" and named only
invite-only groups.

Fixed by moving the logic out of the modal into `Steward.reseatMember` — a re-seat is a seat MOVING, and
everything attached moves with it. The modal now also asks **"lost, or taken?"** at the point of decision,
because the moment the re-seat lands the old key is filtered out of the roster (`src/steward.src.js`,
`reseatOld`) taking the only Block control with it. Before this, a stolen phone kept reading the church,
posting to it, and holding the group keys, for ever.

### The other three

* **Media key.** `mediaEncryptor`'s guard tested whether the relay was AUTHENTICATED. Auth is one round trip;
  the document corpus is not. A console restored from the 12 words could be authenticated and writing while
  the envelope was still in flight — an upload then minted a fresh key and REPLACED the envelope, making every
  sermon the church had ever encrypted permanently undecryptable, with a successful-looking upload. Now uses
  the care key's `_mediaKeyChecked` rule verbatim. Second half: a late envelope no longer discards a key this
  device already holds.
* **Seed in the cache.** Invite links carry the phrase in the URL *fragment* "precisely so it never persists"
  — true of the network, false of Cache Storage, which keys on the full URL. `sw.js` now clears the fragment
  for every cached request. Web/PWA only; `sw-register.js` skips native.
* **Silent relay.** `store.put` THROWS when the store refuses a write; the throw escaped into the
  process-wide handler, so the event was lost, the client got **no reply at all** (a publish that never
  completes, not a rejection), and `/status` kept saying `ok:true`. Now: the client is told, `ok` means
  "doing its job", and `/status` carries a free-space reading.

## Left for review — `fix/backup-file-2026-08-02`

The backup file is the one artefact that deliberately leaves the security model: everything else lives on a
relay the church controls, and a file in a cloud drive cannot be recalled. It carries the member's **twelve
words** — whoever opens it IS them, and the seed unwraps the church's group keys from the relay, so one
cracked file opens the congregation's private conversations, not one person's notes.

Fixed: the passphrase floor now lives in `encryptObj` (it was stated as 6/6/**4** across three screens and
enforced by none — `encryptObj` accepted `""`); all-digit passphrases refused; backups sealed at 64 MiB/t=3
rather than the interactive 19 MiB/t=2; restore filtered through the export's own allowlist (it previously
wrote ANY key, and the "this replaces your account" warning was bypassable by omitting one field); a file with
no `kind` refused; KDF parameters clamped on the way in; and the copy rewritten to say what the file is.

**Four things a reviewer should weigh — these are judgement calls, not measurements:**

1. **The 12-character floor and the no-digits rule are my choice.** Old files still open, but anyone using a
   short passphrase today cannot make a NEW backup until they change it.
2. **The KDF cost is UNTESTED ON A REAL LOW-END PHONE.** I picked ~3× the interactive profile reasoning from
   the comment in `src/recovery.src.js`. If it is too slow or fails on a cheap Android WebView, members cannot
   back up at all — worse than the problem. **This is the one to measure before merging**, and it is a
   two-minute check once a phone is free.
3. **The steward-restore change is not exercised end to end.** It stops the old device's key wrap being put
   back over a restored key (which left a console permanently locked). Read from the code; no test, not driven
   in a browser.
4. **The copy is my wording.** *"Anyone who opens it is you — keep it like a spare front-door key."* Honest;
   tone is the owner's call.

## Still open from the backup/restore audit — on no branch

* **A relay rebuilt on a new machine can come back as an OPEN DOOR.** If the church was configured by
  environment variable rather than the dashboard, that fact is never written to disk, so the backup cannot
  contain it. Restore without re-setting it and the relay accepts writes from anyone and the congregation
  cannot read its own membership — while reporting itself healthy. Fix: persist it at boot
  (`persistChurches()` already exists), and have `/relay-restore` refuse an archive without it.
* **The database side-file trap.** Data is written to `relay.sqlite-wal` first and folded in later, and
  nothing closes the store on shutdown. A hand-copied `relay.sqlite` opens **without error** and contains
  **nothing**. `reference/PILOT-CHECKLIST.md` names that exact file as "holds ALL church data". The official
  backup button is correct (it checkpoints first) — the trap is only for hand-rolled copies. Fix: a
  SIGTERM/SIGINT handler that checkpoints and closes, and correct the checklist to say the whole directory.

and `help-data.jsx` tells members the relay "only ever holds ciphertext" a few lines after correctly
explaining it sees who messaged whom and when.

## Method notes that cost real time today

* **A behavioural test caught a bug in my own fix that a structural one would have passed.** The relay
  storage-failure fix called `send(...)`, which does not exist in that scope — so the catch threw a
  ReferenceError and the client got silence *anyway*. The guard read correctly. Only publishing a real event
  and waiting for an answer found it.
* **My own test was red for the wrong reason.** The parent-DM assertion had no membership fixture, so the
  relay was refusing on membership, not safeguarding. It now joins all three keys and asserts a CONTROL (the
  parent CAN reach the child before the reconnect) so a later refusal can only be the guardian link. Always
  add the control.
* **`data-integrity-guards` failed on my change, correctly.** It anchored on the first textual match of
  `setAdmitted(`, which became `reseatMember`'s CALL to it. Re-anchored on the declaration. This is the
  documented "anchor on the declaration, not a call site" trap, and it caught me.
* **A lifted function's callees must travel with it.** Adding `_beatsDoc` broke 12 tests in three harnesses
  until it was lifted alongside `_topWeMustAnswer`; the failures looked like a code break.
* **`pkill -f "gateway.mjs 9300"` kills your own shell** — the pattern matches the pkill command line.
* **Node's brace-matching lifts must skip `//` comments**, or an apostrophe inside one ("the relay's") opens a
  phantom string and the matcher runs off the end.
* **Audit worktrees can arrive at a stale commit.** Several agents reported being checked out at `41765a2`
  (release 0.7.2) and moved themselves to `main`. Always have them report the sha they audited.

## The pilot path, in order

1. **Two-device safeguarding test** — mark a child on one phone, confirm the child's phone reads it, unmark,
   confirm it clears. Then a re-seat, now that it carries safeguarding. This is the only thing harnesses
   cannot close.
2. **Deploy `main` to a8**, then repeat the device check against the real relay.
3. **The things you cannot undo**: the release keystore off this box (`android/app/release.keystore`, gitignored
   — lose it and no update can ever install on any phone again); a periodic off-box relay backup (the manual
   button works and was driven end to end, but there is no schedule); and the fact that the 12-word backup is
   skippable and unrecoverable.
4. **Go-live switches**: build with `TRINITY_DEBUG=0` (WebView debugging is ON — the build prints a warning),
   and a pre-transpiled build or `STRICT_CSP=1` (the gateway prints a warning that CSP is lax and the console
   holds the church key).
5. **A dry run with real people on a thin link**, and each church marks its minors and cleared adults BEFORE
   any under-18 uses it. That last one is a process step, and it is what makes all of this actually protect
   anyone.
